# 地图 Despec 工作流（Reverse Map Spec Workflow）

> 定位：把"已有地图代码 → 设计意图"逆向还原为标准 spec 文件，使**没有 spec 的存量地图**
> 接入 spec 工作流，之后 agent 就能用 spec 工作流安全地修改、重实现。
> 与 spec 工作流（需求 → 代码）互为反向；**存量图改造工作应先走本技能**。

## 适用场景

- 接手一张老图（没有 spec）：改造剧情、加关卡线、调整触发归属；
- 改造他人制作的地图（先搞清它到底怎么运作的）；
- 从成品图学习设计手法（把别人的图"读"成设计文档）；
- spec 丢失或从未建立，需要重建设计意图留档。

## 核心概念

- **反向三段**：盘点（代码里有什么）→ 解读（这些代码意味着什么）→ 固化（写成 spec）。
  与 spec 的正向三段（故事 → 剧本 → 实现）方向相反，因此**解读先行**：
  先有证据，后有设计。
- **证据驱动**：每条推断必须能指回地图里的具体触发器和参数；推断细节不写进 spec，
  全部进分析报告。
- **spec 纯净**：`mymap.spec.md` 只含用户确认过的设计（格式与 spec 工作流完全一致）；
  证据表、置信度、分歧点、孤儿清单都在 `mymap.despec.md`。
- **用户叙流（不完全可靠参考）**：盘点后请用户用自然语言描述地图整体流程。
  命名、顺序、兵力细节都允许偏差。叙流能揭示代码看不到的关联——例如玩家的部队沿
  一条路前进、途中几波伏兵：这些伏兵触发在代码上可能毫无联系、看上去孤立，但地形
  约束使它们事实上串行。叙流是解读线索，**永不单独作为 depends_on 的依据**。
- **分歧点三分法**：解读中代码与叙流不符时，可能是①用户记错、②疑似代码 bug
  （如启用条件写错导致触发永不生效）、③agent 理解错。**一律登记**进分歧清单，
  逐条向用户对质，不武断忽略。
- **逆向不改地图**：despec 只还原设计意图，不修改任何地图代码；修复/重实现是
  之后的 spec 工作流决策（由用户决定）。

## 工具用法（MCP `despec` 工具，6 个 action）

所有 action 都需传 `map_path`（地图完整路径，正斜杠）。返回 JSON：
`{"ok":true,...}` 或 `{"ok":false,"error":"..."}`。

| action | 必需参数 | 说明 |
|--------|---------|------|
| `inventory` | — | 盘点 [Triggers]/[TeamTypes]/[TaskForces]/[ScriptTypes]/[Tags]/[Waypoints]/[CellTags]/[Houses]/[VariableNames]，返回规模概览与每个触发器的基本信息（名称、所属方、禁用、事件/行为数、标签） |
| `graph` | — | 依赖图。**硬边**（→ depends_on）：行为 53 允许触发、22 强制启动；**终止边**（只标注）：12 摧毁触发、54 禁止触发；**弱证据**（聚类/理解用）：小队 4/5/7/80、变量 28/29/56/57、标签 70、路径点、事件引用、关联触发链。硬边环检测 |
| `draft` | — | 生成草稿 spec data（不写文件）：启发式聚类流水线（所属方 + 连通分量 + 共享引用），每条触发一个条目，summary 为机械摘要，depends_on 只取硬边，每条目带**置信度**（high/medium/low），附故事草稿与疑问清单 |
| `analyze` | `trigger_id` | 单触发器深挖：解码全部事件/行为参数，用于复查存疑条目 |
| `import` | `data` | 把确认后的完整 spec data 校验并写入 `mymap.spec.md`；**已存在则拒绝覆盖**。此后该图由 spec 工具管理 |
| `report` | `user_flow?`, `discrepancies?` | 生成/更新 `mymap.despec.md`：触发器证据表、依赖图、叙流原文（标注"用户提供，未验证"）、分歧点清单、孤儿清单 |

### 会话示例

```
despec(inventory, map_path="C:/maps/old.map")   # 规模概览
despec(graph)                                    # 依赖图
# ← 用户叙流："苏军从北面压过来，路上三波伏兵…"
despec(draft)                                    # 草稿 + 置信度 + 疑问
despec(analyze, trigger_id="0100002")            # 深挖存疑触发器
# ← 与用户逐流水线确认理解、故事、分组、命名、依赖；分歧点逐条对质
despec(import, data={...})                       # 写入 spec（一次性）
spec(validate, map_path="C:/maps/old.map")       # 全量体检
despec(report, user_flow="...", discrepancies=[...])
# ← 汇报孤儿/未纳入清单；之后走 spec 工作流
```

## 标准工作流（6 步）

**① 盘点**：`despec(inventory)` + `despec(graph)`，向用户汇报地图规模与结构概览
（几个触发、几条硬边链、多少孤儿）。**逐层确认从这里开始**。

```
① 盘点       despec(inventory) + despec(graph)
                 → 向用户汇报地图规模与结构概览
     ↓
② 用户叙流     用户用自然语言描述地图整体流程
             （明确告知：不完全可靠的参考——命名、顺序、兵力细节均允许偏差）
     ↓
③ 解读       despec(draft) + analyze 深挖存疑项
             → 以叙流为线索、以代码为证据逐流水线解读：
             · 叙流提示代码看不到的关联（如道路伏兵 → 归入同一流水线，
               叙流推断的顺序依赖标"需确认"，确认后才写入 depends_on）
             · 代码与叙流冲突 → 记入分歧点清单（三分法分类），不武断丢弃
             · 存疑触发用 te_ 系列函数读"编辑器语义"：te_get_event_type(n) 
     ↓
④ 确认       故事 → 剧本 → 分组/命名/依赖 → 分歧点清单逐条与用户对质
             （用户可裁决"接受现状"→ deferred 留档）→ 多轮修改直至用户确认
     ↓
⑤ 固化       despec(import) → spec(validate) → despec(report)
             → 汇报孤儿/未纳入/未解析清单
     ↓
⑥ 接续       之后完全走 spec 工作流：改剧情、重实现、修正推断错误
             （update_entry / link_trigger / set_status）
```

要点：
- **逐层确认**：盘点概览、解读理解、故事、剧本、每个分歧点，都要经过
  "产出 → 用户确认 → 修改 → 再确认"的循环；
- **import 前无未对质项**：分歧点要么 resolved（已对质），要么用户明确
  "接受现状"标 deferred；不允许存在从未向用户展示过的分歧点；
- **import 不覆盖**：若 `mymap.spec.md` 已存在，`import` 报错——先 `spec(read)`
  与用户确认是继续还是重建；
- **状态语义**：逆向导入的条目 status = `implemented`（对应触发器确实存在于地图）；
  用户实测确认理解无误后 `set_status(verified)`。

## 分歧点三分法（细则）

解读中代码与叙流不符时，按三种可能分类，**一律登记**（用户说法 / 代码证据 /
分类 / 状态），在 ④确认 步逐条与用户对质：

1. **用户记错** —— 以代码为准，叙流修正后继续；
2. **疑似代码 bug**（如启用条件写错导致触发永不生效）—— 标注"按原样还原"还是
   "之后通过 spec 工作流修复"（修复 = 重实现决策，由用户定），despec 阶段不改地图；
3. **agent 理解错** —— 回到代码重新解读，必要时 `analyze` 深挖。

## 常见坑

1. **触发名不可靠**（老图命名混乱）：一切推断以事件/行为参数为准，名字只做提示；
2. **depends_on 只取硬边**：小队/变量/标签/路径点引用是弱证据，不写进 depends_on
   避免假串行；叙流推断的顺序依赖（如地形约束下的伏兵串行）须用户确认后才写入；
3. **代码与叙流冲突不武断忽略**：三分法分类、登记分歧清单、逐条对质；
4. **疑似代码 bug 不顺手修**：despec 阶段不改任何地图代码；
5. **逆向 ≠ 重构**：despec 只还原设计意图；不借机"优化"触发、不合并/删除任何东西；
6. **孤儿/未解析项必须进报告清单**，不许静默丢弃；未归类触发由 agent 决定并入
   某流水线或排除出 spec（排除的进报告"未纳入"清单）；
7. **机械摘要 ≠ 语义**：draft 的 summary 是 ASCII 机械摘要（如
   `ReinforceAtWP(team:01000002,wp:25)`），需要你在解读中改写成人类可读的中文
   描述并让用户确认；未知事件/行为 ID（E<n>/A<n>）查
   `knowledge/trigger_and_script/events_params.md` 与 `actions_params.md` 补全；
   **看不懂某触发在做什么时，优先用 te_ 系列函数**（te_get_event_type /
   te_get_action_type / te_select_event / te_select_action / te_get_event_options /
   te_get_action_options）读编辑器语义，别只靠裸参数字典硬猜——te_ 能直接给出类型
   的详细说明和参数的可用选项，比查表更准更快；
8. **编码约定**：地编内部 GBK，外部 UTF-8（.despec_lib.lua 与 .spec_lib.lua
   的注释有完整约定）；触发名从地图读出是 GBK，写入 spec 文件自动转 UTF-8；
9. **多模式图**（遭遇战/战役/多人）：流水线按机制分，故事只写主模式，其余进报告；
10. **修改必须留档**：任何对 spec 的修改（哪怕是纠正推断错误）都用 spec 工具，
    禁止手写 spec 文件——格式漂移是跨会话协作的头号杀手。

## 与 spec 工作流的关系

- despec 的产出就是 spec 的输入：`import` 走 `.spec_lib.lua` 的同一文件格式与
  校验（版本、ID 规则、环检测、触发器存在性），保证单一来源；
- 接续修改一律用 `spec` 工具（update_story / update_entry / link_trigger /
  set_status / validate）；
- 报告文件 `mymap.despec.md` 是参考留档：证据已固化后可以删除，spec 不受影响。
